# NOVA API Contract v2.1

Updated November 7, 2026. This replaces v0.1. Frontend and backend must both report/use `contract_version: "2.1"`. v2.1 only adds `GET /live` (section 9b) to v2.0; every v2.0 shape is unchanged. The endpoint names are retained where practical; the richer configuration and run objects are a breaking schema change. The ByteShape implementation is now in `backend/src/nova_backend`; see `backend/README.md` for run commands and current adapter limits. Glimmer and Flash execution remain deferred.

Repository: https://github.com/SoLLLLLZ/NOVA_TT

Repository paths: contract `docs/api/endpoint.md`; model reference `docs/demo/DEMO_MODELS.md`; agent prompt `backend/prompts/OPTIMIZER_AGENT.md`; evidence `data/canon/`. Mock implementations belong in `tests/mocks/`.

The normal UI stays simple: select model and hardware, Optimize, see verification and decode speed. Advanced settings are available through typed capabilities and a details panel; the UI does not need a slider for every field. The backend resolves artifacts, schedules work, calls the agent, applies complete configurations, verifies them and owns rollback.

## 1. Transport, authentication and versioning

- Local/tunneled base URL: `http://localhost:8000`. Bind backend and model services to loopback; access Wright services through the backend's private connection.
- JSON request/response bodies; POST streaming uses `text/event-stream` and `data: <JSON>` followed by a blank line. Use fetch streaming, not EventSource for POST.
- Every request except `GET /health` requires `X-Pairing-Token`. Keep OpenRouter credentials solely in backend secret storage, never in browser code, prompts, URLs, logs or response objects.
- Mutation requests (`/optimize`, `/race`, `/revert`, `/action`, `/runs/{run_id}/cancel`) require an `Idempotency-Key` generated by the client. Retain the key through retries. Repeating the same key/body returns the same run/result and never launches again; a different body with that key returns 409 `idempotency_conflict`. Deduplicate for the backend session lifetime; recover state after a backend restart before allowing work on existing owned allocations.
- Responses may add optional fields within v2; clients ignore unknown response fields. Unknown request fields, unsupported overrides and invalid types are rejected explicitly, never silently dropped.
- Omitted optional input means preserve the chosen profile/default. Explicit null is accepted only for nullable fields whose meaning is defined below. Zero, false, empty array and null are distinct. A null observation means unknown/not measured, never zero performance.
- HTTP errors use 400 for invalid input, 401 for pairing, 404 for unknown IDs, 409 for conflicts/availability, 422 for incompatible settings, 503 for inaccessible services, and 500 for unexpected failures. After streaming starts, errors use the same object inside a terminal `error` event.

Error shape: `{"error":{"code":"unsupported_setting","message":"Draft size 17 exceeds this Glimmer runtime's limit of 15.","diagnosable":true,"retryable":false,"field":"settings.draft_tokens","details":{"maximum":15}}}`. `field` and `details` are optional, sanitized structured data. Codes include `unauthorized`, `bad_request`, `not_found`, `model_not_found`, `runtime_unavailable`, `unsupported_setting`, `constraint_violation`, `out_of_memory`, `gpu_busy`, `allocation_unavailable`, `ssh_unavailable`, `operation_in_progress`, `idempotency_conflict`, `benchmark_failed`, `validation_failed`, `ai_unavailable`, `deadline_exceeded`, `cancelled`, `rollback_failed`, `internal`.

## 2. Core objects and meanings

### Config: complete selected profile, not a small UI allowlist

`config` contains `profile_id` (immutable backend profile ID, null before resolution), `model` (catalog ID), `artifact_id` (registered target artifact), `quant`, `engine` (`ollama` or `llama.cpp`), `runtime_id` (registered binary/library bundle), and `settings` (the fields below). The profile ID resolves the full model/draft/runtime/template/settings combination, not just a CANON row. Overrides produce a new profile revision/ID. Artifact/runtime IDs are returned by the backend catalog; clients never fabricate paths or assume CANON `runtime_ref` is executable.

See [DEMO_MODELS.md](../demo/DEMO_MODELS.md) for the three model IDs and concrete v2 config examples. A resolved config also has `unresolved_fields`, an array of `{path,reason}` (empty when fully resolved). A proposed config can omit that array. In any `changes` array, paths are relative to config, such as `settings.draft_tokens`; each entry carries the old value, new value and a short reason. For the ByteShape production-to-candidate transition, show draft_tokens 3 -> 5 and temperature 1 -> 0.75 separately.

`source_config_ids` and `lesson_ids` live in the separate `evidence` object. A source configuration ID is historical provenance, not proof the effective config is identical. Record any deviations. Preserve native runtime provenance and requested/effective settings; never silently clamp a requested value. If the runtime resolves auto/default values, report the resolution and revalidate constraints.

All settings below are representable by the contract. **Representable does not mean supported by every model, runtime, allocation or adapter.** `/capabilities` defines current writable fields, domains, dependencies and restart requirements. The agent can use the same full schema as the backend. The frontend may display all fields but edit only capability-approved ones. Backend policy can restrict automatic selection to proven profiles while still exposing experimental controls for explicit requests.

### Core settings (CANON-aligned names)

Except where noted, fields live under `config.settings`. Requests can submit a partial `overrides.settings`; resolved configs contain every applicable setting required to reproduce that profile. Unknown effective values are null plus an explanation in `unresolved_fields`; if needed for safe launch, they block execution.

| Field(s) | Type / meaning | Application and validation |
| --- | --- | --- |
| `context_tokens` | positive integer, total context allocated per process | CANON's total, not automatically per slot |
| `context_per_slot` | positive integer, usable context per request slot | Must satisfy caller minimum; adapter checks actual total/slot relationship |
| `context_override` | array of `{key,type,value}` metadata overrides | Registered model keys/types only; never parse CANON's comma string as shell |
| `parallel_slots_per_process`, `replicas` | positive integers | Slots per server versus independent server processes; validate each replica's resource map |
| `gpu_layers` | nonnegative integer or `"auto"` | Requested target offload; actual loaded/total layers are separate observations |
| `main_gpu` | nonnegative integer, allocation-local ordinal | Must be in the selected allocation |
| `split_mode` | enum advertised by runtime, including none/layer | Row split only if runtime/model supports it |
| `tensor_split` | array of nonnegative relative weights | Length matches selected devices; at least one positive; preserve order |
| `tensor_overrides` | array of `{pattern,buffer}` | Validated tensor pattern and allocated buffer such as CUDA0; no arbitrary expression execution |
| `batch_size`, `microbatch_size` | positive integers | Logical batch / physical microbatch; microbatch <= batch unless adapter explicitly documents otherwise |
| `threads_decode`, `threads_prefill` | positive integers | Separate CPU workloads; validate against policy/allocation, record intentional oversubscription in default baseline |
| `kv_type_k`, `kv_type_v` | runtime-advertised strings | Distinct K/V target caches; formats may include f16, q8_0, q4_0, but model/kernel support controls choices |
| `flash_attention` | `"on"`, `"off"`, `"auto"` | Effective state returned separately when auto |
| `fit` | `"on"` or `"off"` | Fit must not silently reduce promised context or violate headroom |
| `fit_target_mib` | array of positive integers | One value broadcast to all devices or one per device; adapter normalizes to a per-device array |
| `speculative_mode` | runtime-advertised enum | Demo: none, draft-mtp, draft-dflash; ngram-simple and other modes only when supported |
| `extra_speculation` | object `{modes: string[], parameters: object}` | Additional combined methods and typed n-gram controls; capability lists valid keys/combinations |
| `draft_model` | registered artifact ID or null | null means no separate draft artifact (e.g. an integrated MTP head); not an arbitrary filename |
| `draft_device` | array of allocated device names | e.g. `["CUDA0"]` or `["CUDA2"]`; never global GPU indices |
| `draft_tensor_overrides` | array of `{pattern,buffer}` | Same validation as target overrides |
| `draft_gpu_layers` | nonnegative integer or `"auto"` | Draft offload; requested 99 and observed 6/6 are different facts |
| `draft_tokens` | nonnegative integer | Maximum speculative draft size; model/runtime-specific ceiling; effective Glimmer ceiling is 15 for the pinned draft/runtime |
| `draft_probability_min` | number in [0,1] | Draft acceptance/proposal threshold as interpreted by this runtime |
| `draft_kv_k`, `draft_kv_v` | runtime-advertised strings | Draft K/V cache formats, independent of target |
| `backend_sampling` | boolean | Native backend sampling where supported |
| `cuda_launch_queues` | adapter-defined registered enum/string | CANON contains `4x`; mapping requires the matching runtime implementation, not a generic flag guess |
| `mps` | boolean | Expose capability; no shared MPS daemon changes on Wright; unsupported/restricted by default |
| `force_mmq_runtime` | boolean | Native runtime control, e.g. registered FLASH_NEXT_FORCE_MMQ mapping; not a compile-time toggle |
| `load_mode` | advertised enum | Installed source declares auto, none, mmap, mlock, mmap+mlock, dio; availability depends on runtime/filesystem |
| `lazy_mode` | advertised enum | Installed source declares auto, on, off, on-direct; architecture/build conditions apply |
| `prompt_cache_ram_mib` | nonnegative integer or advertised sentinel | Host RAM cache budget, distinct from GPU KV; constrained by allocation |
| `checkpoint_min_step` | nonnegative integer | Cache checkpoint spacing; retain native semantics and supported range |
| `temperature` | nonnegative number | Sampling distribution change; include it in UI change details |
| `top_k` | nonnegative integer | Zero meaning disabled only where runtime defines it |
| `top_p`, `min_p` | numbers in [0,1] | Runtime-specific edge constraints still validated |
| `reasoning_effort` | model/runtime-advertised enum | Target GPU model's reasoning, not OpenRouter Astra's reasoning |

Model/quant/engine/runtime choices are first-class config fields. `model_file` and `vision_projector` are read-only artifact metadata resolved from `artifact_id` and `settings.vision_projector` (registered projector ID or null). Changing quant selects another installed compatible artifact; it does not requantize/download inside the demo by default.

`runtime_options` provides forward coverage for additional real runtime parameters without a version bump per flag. A key must have an explicit descriptor and executable adapter mapping; absent mappings return `unsupported_setting`. New fields that change core semantics still require a versioned contract update. Training, embedding/evaluation utilities, arbitrary model downloads, credentials, remote RPC targets, web/MCP tools and public networking switches are not inference-speed tuning controls for this product. Synthetic speculative acceptance controls (`spec-synth-*`) are benchmark-only diagnostics: if ever exposed, label synthetic output and exclude it from real speed/quality claims.

Canonical names in these tables are API names, not a promise that spelling maps directly to a CLI flag. The adapter maps them explicitly (for example threads_prefill -> --threads-batch, draft_tokens -> --spec-draft-n-max). Some declarations in common/arg.cpp apply only to particular executables. Do not enable a field on the server just because it appears somewhere in the common source.

### Build identity and cluster resources

Compile settings are not mutable server flags. `runtime` catalog entries include `runtime_id`, `runtime_variant`, `runtime_ref`, binary/library/source identities, CUDA architecture/version, and `build_features` with `cuda_graphs_build`, `force_mmq_build`, `force_cublas_build`. Optional `constraints.runtime_requirements` contains these booleans to select a matching installed build. Report unsupported requirements; do not compile during a five-minute demo. Runtime/library identity is preserved even when historical CANON runtime hashes are shared across profiles.

`resources` is the allocation request, separate from settings:

| Field | Type / meaning |
| --- | --- |
| `target_id` | ID advertised by status, e.g. `wright` |
| `allocation_id` | existing owned allocation ID or null to request allocation |
| `gpu_type` | advertised type, e.g. L40 |
| `gpu_count` | positive integer total unique GPUs required for this configuration |
| `gpu_ids` | optional array of opaque IDs returned by backend, scoped to allocation/node |
| `same_node` | boolean; true for the three-GPU Flash profile |
| `replica_gpu_groups` | optional array of arrays of GPU IDs, one group per replica; explicit sharing requires supported contention policy |
| `cpus_per_task` | positive integer |
| `host_memory_mib` | positive integer host memory request |
| `wall_time_seconds` | positive integer allocation lifetime; separate from agent deadline |
| `account`, `partition`, `qos` | catalog-approved scheduler values, not free-form Slurm arguments |
| `power_limit_w` | optional requested per-GPU ceiling only if capability says writable; otherwise observed read-only |

Wright compute uses Slurm device masks. Never launch inference on the headnode, select another user's GPUs or mutate shared daemons. Existing Wright tests used account/partition cmist, QoS cmist_priority, 12 CPUs, 65536 MiB host RAM, and unchanged 300 W L40 limits; these are historical defaults to validate live, not guaranteed availability. `power_limit_w` is read-only on the current Wright adapter. MPS/system clocks/thermal guards are not changeable merely because a database row records them. Expose unavailability honestly. Hardware `gpu` type and observed `gpu_layout` are status/provenance; the structured resource map replaces free-text layout as input.

## 3. Capabilities, profiles and status

### GET /health

No auth. `{"ok":true,"contract_version":"2.1"}` confirms the API process only, not SSH/GPU readiness.

### GET /capabilities?model=...&runtime_id=...&target_id=...

Required model and target; runtime optional to inspect the supported catalog. Returns `contract_version`, `capabilities_revision`, `model`, `target_id`, `runtime_id` (or null), `fields` map, `constraints` array, `artifacts`, `runtimes`, and `resource_options`. Each `fields` key is a dot path such as `settings.draft_tokens`, `resources.power_limit_w`, or `constraints.runtime_requirements.cuda_graphs_build`. Each descriptor provides:

- `schema`: JSON Schema type, enum, bounds, items/properties, additionalProperties and nullable status as applicable.
- `support`: `supported`, `unsupported` or `unknown`; `access`: `writable`, `read_only` or `profile_selection`.
- `apply`: `request`, `restart`, `reallocate`, `select_build` or `observe_only`; `evidence`: `tested`, `source_declared` or `unverified`.
- `reason` string or null; `default` and `effective` when known; `ui_group`, `advanced` boolean; `runtime_mapping` sanitized flag/native-key description.

The backend must publish a descriptor for every field it accepts, including runtime_options keys. Discovery can use saved profile manifests and installed version/help/source, but writable support requires an implemented adapter and compatibility validation. `unknown` fields cannot be silently treated as supported. Cache descriptors outside the critical demo path; refresh when runtime/allocation changes. Cross-field constraints are enforced server-side even if frontend validation is incomplete.

`artifacts` entries contain `{id,model,kind,quant,installed,files}`, with kind target/draft/projector/template/grammar/lora/control_vector. Each file has `{name,size_bytes,sha256,verified}`; hashes/verification can be null when unknown. Names are basenames; paths stay backend-owned. `runtimes` entries use the runtime identity definition above and add installed/support reasons. `resource_options` is an object of approved scheduler values and allocation bounds. `constraints` is an array of `{code,paths,message}` describing cross-field rules; backend code enforces them. With runtime_id omitted, fields are the conservative common subset and runtime-specific alternatives remain under runtimes; fetch with a selected runtime before submitting overrides. `capabilities_revision` identifies the descriptor snapshot; clients may pass it on optimize/action, and stale incompatible revisions return 409 constraint_violation rather than silently reinterpret settings.

      "apply": "restart",

      "reason": null,
      "ui_group": "speculation",

    },
    "resources.power_limit_w": {

### GET /profiles?model=...&target_id=...

Returns `profiles`: each has `profile_id`, `label`, `config`, `resource_requirements`, `evidence`, `compatibility` (`compatible`, `incompatible`, `unknown`), and `reasons` string array. Resolve complete saved launch/template settings through registered assets. Listing is read-only and does not apply profiles. Include the three models in DEMO_MODELS.md; represent production and tested candidate variants separately.

### GET /status

Return `contract_version`, `observed_at` (ISO 8601), `target_id`, `connection` (`connected`, `disconnected`, `unknown`), `allocation`, `all_gpus`, `models`, `current_config`, `active_run_id`, `is_tuned`, `contribute_results`, and `optimizer_agent`.

- `allocation`: null or `{id,state,node_ids,gpu_ids,cpus_per_task,host_memory_mib,expires_at,owned}`; states `pending`, `running`, `completed`, `failed`, `unknown`. Only allocated accessible GPUs are selectable. `all_gpus` may be empty before allocation; do not confuse this with no cluster GPUs.
- Each GPU: `{id,node_id,local_index,label,name,memory_total_mib,memory_free_mib,busy,power_limit_w,temperature_c}`; unknown telemetry is null. Memory units are MiB, not ambiguous GB. Physical UUIDs may be retained internally.
- Each model: `{id,display_name,quant,artifact_id,installed,loaded,database_coverage,requirements,ready,readiness_reasons,race}`. Coverage is `verified`, `inferred`, `experimental` or `none`; ready is true only after current dependencies/resources are checked. `requirements` includes gpu_type, gpu_count, same_node and context_per_slot. `race` has `simultaneous_available` boolean, `sequential_available` boolean, `required_gpus_simultaneous` integer and `reasons` array. Missing assets/runtime and queueing are separate reasons.
- `current_config`: null or full effective config. `is_tuned` is not inferred just from model presence; it reflects the backend's applied verified optimized profile.
- `optimizer_agent`: `{model,reasoning_effort,requested_service_tier,effective_service_tier,available}`. Astra high through OpenRouter; no secret or hidden reasoning. This is separate from the GPU model's `settings.reasoning_effort`.

Download presence does not imply loaded, allocated or ready. Database confidence does not imply today's test passed. Expose connection, allocation and dependencies so the frontend can explain an unavailable action.

## 4. POST /optimize (streaming)

Select a conservative compatible profile, apply it, verify a completed answer and retain the working service. Default objective is decode, preset fastest, workload short. Optional sequential baseline benchmarking is explicit.

Current ByteShape demo adapter: the throughput prompt is exactly `Write a short essay explaining the causes of the Industrial Revolution`, with a 256-token output cap. A separate arithmetic task checks basic correctness. `workload` selects short/long historical CANON evidence; it does not repeat or alter this demo prompt. For the live essay race, submit that exact prompt to `/race` with `max_tokens: 2048`; natural stopping is enabled, and completion status must remain visible if the cap is reached.

Request example:
```json
{
  "model": "qwen3.8-27b",
  "preset": "fastest",
  "objective": "decode",
  "workload": "short",
  "mode": "sequential_compare",
  "resources": {
    "target_id": "wright",
    "allocation_id": null,
    "gpu_type": "L40",
    "gpu_count": 1,
    "same_node": true,
    "cpus_per_task": 12,
    "host_memory_mib": 65536,
    "wall_time_seconds": 3600
  },
  "constraints": {
    "min_context_tokens": 32768,
    "quant": "IQ3_S hybrid 3.23bpw",
    "allow_quant_change": false,
    "allow_sampling_change": true,
    "allow_experimental": false
  },
  "profile_id": null,
  "overrides": {
    "settings": {}
  },
  "budget": {
    "deadline_seconds": 180,
    "max_repair_attempts": 2
  },
  "baseline_run_id": null
}
```

Required: model. Defaults: preset `fastest`, objective `decode`, workload `short`, mode `verify_only`, resources selected compatible backend target/profile, constraints preserve model/quant and required context, profile_id null, empty overrides, budget 180 seconds/two repairs, baseline_run_id null. `preset` supports fastest/balanced/quality as selection policies, not fixed engine parameters; caller constraints always win. `objective` currently supports decode; unsupported objectives return 422. `workload` supports short/long, corresponding to the CANON examples. `min_context_tokens` is per request slot, not process total.

`allow_sampling_change` defaults true (project owner authorization, November 7); true permits a tested preset's declared temperature/top-k/top-p/min-p/reasoning changes, all shown in changed/effective config. `allow_quant_change` and `allow_experimental` default false. When no active profile exists, use the registered model's baseline sampler as the preserved reference. Constraints may include `fixed_settings` (partial settings that cannot change), `min_free_gpu_memory_mib` (per-device floor, cannot weaken backend guard), `max_gpu_count`, `runtime_requirements`, and `allow_cpu_offload` (default false). Preserve the current/profile context if no minimum is supplied. Overrides are fixed requested values, not suggestions; reject conflicts with fixed_settings instead of silently deciding precedence. Precedence: host/resource policy and user constraints > explicit profile/overrides > agent selection > defaults.

`overrides` permits `artifact_id`, `quant`, `engine`, `runtime_id`, and a partial settings object. Artifact changes must match the selected model/quant and constraints. `profile_id` selects a base profile; null lets the agent choose. Explicit unsupported values produce field-level errors. A profile not registered on this host cannot be applied solely from an ID in CANON.

`budget.deadline_seconds` must be positive and no greater than the deployment's advertised maximum; max_repair_attempts is an integer 0..2. `baseline_run_id` is valid only in sequential_compare. Constraints.quant is a string or null (null means preserve selected/current artifact quant, not authorize arbitrary quant changes). Specifying resources.gpu_ids requires allocation_id; omitting both allows the backend to resolve a compatible owned allocation or request one. With an existing allocation, resource requests must fit it; do not enlarge or replace it silently. Action requests may also include capabilities_revision at the top level.

`verify_only`: no baseline required; after successful setup return before=null and speedup=null. `sequential_compare`: run untouched Ollama then the selected llama.cpp profile on the same owned allocation, or reuse a compatible baseline_run_id from this demo session with matching hardware/artifact/workload and documented measurement conditions. Never use historical CANON rates as a live baseline. Budget includes baseline, queueing, loading, verification and repairs; do not secretly restart the timer. An expensive queue/download is surfaced immediately. Failed comparison after a valid setup is still an error for this requested mode; preserve the last verified state and report it, never emit a misleading complete comparison.

Automatic repair is authorized inside this operation within constraints and budget. Try the smallest concrete correction or a compatible complete fallback; rerun verification. At most two repairs after the initial attempt. Stop when a working profile is verified. No unbounded optimization sweep, compile or large download by default.

## 5. Shared operation stream and lifecycle

On acceptance return SSE and a `start` event with `run_id`, `operation`, `mode`, `started_at` and `deadline_at`. Store run state before launching anything. Subsequent events include run_id and monotonically increasing `sequence`. Event definitions below list their additional fields; all numerical examples are fixtures, not measured claims.

All operation events include `type`, `run_id`, `sequence` (integer starting at 1), and `at` (ISO 8601). A repeated idempotent streaming POST returns HTTP 200 JSON `{run_id,state,replayed:true,result,error}` instead of creating another stream or reexecuting work; result/error are null while pending. Clients check Content-Type and recover/poll through GET /runs. Pre-acceptance validation errors likewise return ordinary JSON/HTTP status without opening an SSE stream. New accepted operations return the normal SSE stream.

| Type | Fields / semantics |
| --- | --- |
| `start` | operation: optimize/race/action/revert; mode string; started_at and deadline_at |
| `step` | name, status, progress (0..1 or null), detail; steps detect_gpu, check_database, ask_ai, allocate, load_model, test_configs, verify, repair, apply, rollback; status pending/running/done/failed/skipped |
| `config` | phase proposed/effective, full config, changes array, evidence; changes use `{path,from,to,reason}` with dotted config paths |
| `benchmark` | label default/tuned, full measurement object |
| `validation` | full validation object |
| `repair` | attempt, error_code, summary, changes, fallback_profile_id (nullable) |
| `done` | operation-specific final result; terminal success, emitted once |
| `error` | standard error object plus cleanup and last_verified_profile_id; terminal failure/cancellation, emitted once |

For optimize, order is start, progress/proposed config, optional baseline measurements, effective config, verification/measurements, and done; repairs may repeat appropriate steps. Never mark apply done until effective config is checked. No fabricated percentages; progress null is acceptable. Heartbeats are SSE comments and must not reset deadlines.

Keep one mutating operation per overlapping owned resource set. Reject conflicting work with 409 and active_run_id. State changes are saved server-side. A dropped browser stream does not launch another run or reset its budget; the operation continues under backend supervision to its deadline. All long-running tools have deadlines and a cancellation check. Exceeding the deadline aborts this run's attempt and enters bounded cleanup; record cleanup time separately, and surface rollback failure. Never kill unrelated processes.

`cleanup` is `{status,restored_profile_id,retained_service_id,released_allocation_ids,issues,elapsed_seconds}`. Status not_needed/pending/completed/failed; IDs may be null and issues is a string array. Restoration is a measured outcome, not an assumption. Stop failed-attempt services and cancel newly requested owned pending jobs when terminating; retain caller-owned allocations unless explicitly released. A successful retained service is not leaked work: expose its allocation expiry and rollback ownership. Reserve up to 60 seconds for bounded cleanup after the work deadline, and report total elapsed time honestly.

### Measurements

`measurement` contains:

- `measurement_id`, `run_id`, `profile_id`, `origin` (`live` or `historical`), `purpose` (`throughput`, `quality`, `warmup`), `workload`, `prompt_hash`, `request_hash`, `engine`, `runtime_id`, `gpu_ids`, `rate_scope` (per_request/per_agent/aggregate), `cache_state` (uncached/reused/unknown).
- `prompt_tokens`, `output_tokens`, `cached_tokens`, `decode_timed_tokens`, `prefill_seconds`, `decode_seconds`, `wall_seconds`, `load_seconds`, `queue_seconds`, `decode_tps`, `prefill_tps`: nonnegative numbers/counts or null. Throughput denominators must be positive; never emit infinity/NaN. Definitions for decode convention are explicit in `timing_convention`.
- `output_cap`, `stop_reason`, `completed`, `quality_pass` (boolean or null), `min_free_gpu_memory_mib` (map by GPU ID), `peak_temperature_c` (map), `settings_hash`, `artifact_ref` (sanitized result reference), `sample_count`, `warnings` array.

Use native phase timings, not wall time including startup or API-agent latency. A cached request is not cold prefill. Historical data is never injected into live benchmark events. Keep each trial; if reporting pooled rates use total timed tokens / total phase duration only across compatible trials, and identify the aggregate. Native Ollama n/time and this llama.cpp (n-1)/time convention are recorded, not silently treated as identical. Output channel extraction and token counting belong in the backend.

### Validation and evidence

`validation`: `{status,completed_answer,answer_correct,service_healthy,placement_matches,context_matches,memory_guard_pass,configured_context_per_slot,tested_prompt_tokens,checked_at,scope,issues}`. Status pending/passed/failed; checks boolean or null. Configured context is not the length tested: tested_prompt_tokens records the actual input. `scope` describes the actual short completed-answer test, never broad quality or full-context certification. A capped probe/HTTP 200/health check alone is not passed validation. Success requires a correct naturally completed answer and a healthy correctly configured service with headroom.

`evidence`: `{confidence,source_config_ids,lesson_ids,source_rows,match,deviations,cautions}`. Confidence verified/inferred/experimental/none means historical evidence match. `match` records model, quant, GPU type/count, context, concurrency and runtime match booleans or null. Today's validation is independent. Filter record_type=configuration for ranking; lesson rows guide decisions, not numerical predictions. Preserve failure rows as exclusions and never interpret blank measurements as zero.

### Optimize done result

Fields: `status: "success"`, `mode`, `applied: true`, `config` (full effective), `evidence`, `validation`, `before` and `after` (measurement or null), `speedup` (number or null), `comparison`, `reason`, `repairs`, `elapsed_seconds`, `service`, `rollback_id`, `repro_command` (sanitized valid command or null), `repro_ref` (registered reproduction reference or null).

`comparison`: `{available,mode,baseline_run_id,reason,conditions_differ}`. Speedup = after.decode_tps / before.decode_tps only when both positive valid comparable phase rates exist. Round for display, preserve underlying rates. If unavailable, speedup=null and reason explains why. Operational success does not assert faster performance: a measured ratio below 1 is shown honestly. `service`: `{id,state,allocation_id,expires_at}`; success retains the service under backend supervision and the Slurm lifetime, not indefinitely. `rollback_id` resolves exact prior owned configuration/services, not a partial UI snapshot. `repairs` is an array of attempt summaries. `before` remains null in verify_only; after may have null phase rates if engine timing is unavailable, with a measurement warning.

## 6. POST /race (streaming)

Required model and prompt. Optional `mode` simultaneous/sequential (default simultaneous), `max_tokens` positive integer (default 256), `tuned_profile_id` (default current verified profile), `resources` same schema, `budget` (default 180 seconds), and `seed` integer. No silent downgrade from simultaneous to sequential. Requesting sequential explicitly supports the staged presentation; show sequential in the UI.

For race, resources.gpu_count is the total unique GPU request across lanes, while resources.same_node applies within each lane. CPU/RAM fields are per lane and the allocator reserves two sets in simultaneous mode. Returned lane_resources gives the exact mapping; omitting resources lets the backend derive the requirements from model and mode. Auto-repair of an already verified profile is not part of race; setup failures terminate visibly.

The backend owns both lane configurations: untouched default Ollama and the verified optimized llama.cpp profile for the same model artifact. Keep input text/output cap comparable and disclose sampler/template/context/token-count differences. Simultaneous lanes require separate equivalent GPU and CPU resources. ByteShape/Glimmer need 2 L40s total; Flash needs 6 total, 3 on one node per lane. Return allocation_unavailable before launching when requirements cannot be met. Sequential mode reuses one model allocation (1/3/1 GPUs). Do not allow unverified profiles to bypass verification through this endpoint.

Use shared start/step/error envelope, with these additional events:

- `start` additionally supplies `lanes: ["default","tuned"]`, `mode`, and `lane_resources` map with allocated GPU IDs per lane.
- `token`: lane, text, cumulative `tokens`, nullable running `tps`; `tokens` is also nullable while a runtime does not supply incremental counts. Final native counts arrive in lane_done; never substitute string lengths or chunk counts. Deliver parsed user-visible final text; do not forward hidden reasoning or native channel markers.
- `lane_done`: lane, measurement and validation status (a race prompt is not automatically a correctness test).
- `done`: status success, mode, measurements map, winner (`default`, `tuned`, `tie` or null), speedup (nullable), comparison, elapsed_seconds and cleanup. Compare measured decode rates; round only for display. A lane failure terminates with error and partial measurements, not a fabricated winner.

After racing, stop only temporary lane services and restore/retain the pre-race verified tuned service where feasible. Report cleanup and service state. Baseline and race resources never overlap in simultaneous mode, even if a historical CANON row used shared replicas.

## 7. Run recovery and cancellation

### GET /runs/{run_id}

Returns `{run_id,operation,state,sequence,started_at,deadline_at,progress,current_step,latest_config,evidence,validation,measurements,repairs,result,error,cleanup}`. State is pending/running/cancelling/succeeded/failed/cancelled. Nullable fields are null before known. `result` equals the terminal done payload, `error` equals terminal error details. This is a snapshot for reconnect/polling, not an instruction to replay POST. Unknown run ID returns 404.

### POST /runs/{run_id}/cancel

Body `{}`. Returns 202 `{run_id,state:"cancelling"}` while stopping owned work; terminal runs return 200 with their existing state. Idempotent. Cleanup restores the last verified owned state when possible; cancellation never cancels another run's allocation. The original stream terminates with error code cancelled; run state becomes cancelled only after cleanup status is recorded. Expose rollback_failed separately if restoration cannot be verified. This endpoint cancels the operation, not a successful retained service; use revert for that.

## 8. POST /revert (streaming)

Body `{"rollback_id":"<ID returned by optimize/action>"}`. Required ID avoids reverting the wrong model/run; support only owned backend snapshots. Same start/step/done/error lifecycle, with operation revert and backend cleanup budget (default 60 seconds, published in capabilities). Validate prior dependencies and allocation before changing anything. `done`: `{status:"success",restored:true,config,service,validation,elapsed_seconds}` plus stream envelope. If previous state was unloaded, config/service can be null and validation scope is restoration-to-unloaded; do not falsely claim a completed-answer check. Restoration errors report actual remaining service state. Reverting does not change historical measurements.

## 9. POST /chat (streaming)

Request `{message,history?,model?,run_id?}`. history is an array of role/content pairs; caller content is untrusted. Backend supplies current config, evidence, capabilities and run results. Emit delta `{text}` then done `{suggested_questions, suggested_actions}` or error; run_id may be null for chat. Suggested action objects follow diagnose below. Chat does not execute configuration changes without an explicit optimize/action request. Keep user-facing explanations short; never expose secrets or hidden reasoning. OpenRouter failure returns ai_unavailable, not fabricated advice attributed to the model.

## 9b. GET /live (streaming, added in v2.1)

Lets the widget reveal real speed once the student runs the tuned model from their own terminal. Query `model` (required, catalog ID). Authenticated like every other route, so clients read it with fetch streaming (EventSource cannot send `X-Pairing-Token`). It reports activity on the backend-retained optimized service for that model; it starts nothing and changes nothing.

Before streaming: unknown model returns 404 `model_not_found`; no retained optimized service for that model returns 404 `not_found` ("No optimized service is running for this model."). Otherwise the response is `text/event-stream` and stays open across many requests until the client disconnects. Heartbeats are SSE comments. Events carry `type`, `sequence` (per connection, from 1) and `at`:

| Type | Fields / semantics |
| --- | --- |
| `waiting` | model, service_id; sent once on connect while no request is in flight |
| `inference_started` | request_id, model, service_id, prompt_tokens (nullable); a request reached the tuned service |
| `metrics` | request_id, decode_tps, prefill_tps (nullable numbers), output_tokens, timing_convention; running native-engine rates during generation, at most ~4 per second |
| `inference_done` | request_id, measurement (full measurement object above, origin `live`) |
| `error` | standard error object; e.g. the service was stopped or reverted. The stream ends after it |

Rates come only from the live engine timings of requests to the retained service; never emit historical CANON rates, estimates or the optimize benchmark here. Prefill may be null until the prompt phase finishes. Requests that bypass the retained service (for example a separate Ollama process) are not reported. The mock implements a non-contract `POST /mock/inference` to simulate a terminal request; the real backend does not expose it.

## 10. POST /diagnose

Request `{model,run_id?,error_code?,log_tail?}`; prefer server-owned logs and sanitize any user log. Read-only. Returns `{explanation,can_auto_repair,suggested_action}`. suggested_action is null or `{action,params,label,constraint_changes}`. Allowed actions: apply_config, revert, lower_context, switch_quantization, run_benchmark. `constraint_changes` explicitly lists changes needing a fresh user action; diagnose itself never applies them.

Auto-repair inside optimize does not require clicking this endpoint. It is already authorized within that run's constraints. Lowering the user's promised minimum context, changing a locked quant or stopping unrelated work is never an automatic repair.

## 11. POST /action (streaming)

Body `{action,params,budget?}` plus Idempotency-Key. Same validated runner, locking, verification, progress and rollback as optimize; no alternate unsafe execution path. Params:

| Action | Params |
| --- | --- |
| `apply_config` | model, profile_id, overrides?, resources?, constraints?; override schema exactly as optimize |
| `revert` | rollback_id |
| `lower_context` | model, context_per_slot, profile_id, resources?; explicitly revises that constraint; backend computes total context and validates draft/model limits |
| `switch_quantization` | model, artifact_id, profile_id, resources?, constraints?; installed artifact only by default |
| `run_benchmark` | model, profile_id, resources?, workload (short/long), purpose (throughput/quality), max_tokens?, seed?; no implicit profile promotion |

`done` for apply/lower_context/switch_quantization uses the optimize verify_only result (with operation action). Revert uses revert result. Benchmark returns `{status:"success",measurements,validation,applied:false,service,cleanup,elapsed_seconds}`; a failed required quality check terminates with error. Unknown actions return bad_request. Never accept raw commands, arbitrary environment variables or user-supplied executable paths.

## 12. Validation rules and demo policy

- Validate artifact identity, target/draft architecture compatibility, runtime/library bundle, supported flags and resource fit before launch. Resolve all shards and registered projector/draft artifacts. CANON's filename alone does not prove installation.
- Validate per-device memory/headroom, not summed VRAM alone. GPU masks/local indices derive from Slurm; opaque frontend IDs are mapped by the backend. GPU count/layout/same-node requirements apply to every replica and race lane.
- Preserve context, quant, quality and explicitly fixed sampling constraints. Auto-fit cannot silently shrink below min_context_tokens. Record total process context and usable per-slot context separately.
- For ByteShape/Glimmer short-prompt candidates, changing both draft size and temperature must produce two changes in the stream. Keep decode/prefill thread counts and K/V types independent. The runtime cannot silently ignore unsupported Ollama/llama.cpp fields.
- Exact Glimmer draft/runtime cap is 15; other draft ceilings are discovered per model/build. A general integer range never overrides actual trained/runtime limits.
- Build flags choose registered binaries; power/system/MPS restrictions remain explicit capabilities. Avoid source builds/downloads in the live operation. API representation is broader than the conservative agent's auto-selection policy.
- Reproduction requires runtime/library identities, actual resolved settings, artifact hashes from verified manifests, template, sampler, resource map and request/measurement details. Store a sanitized manifest per run; do not run expensive full-model hashing on the login node to recreate it during a demo.
- Prefer one known compatible candidate plus one fallback, short validation, at most two repairs, and stop after success. Failed attempts stay in run history. A pending queue, disconnected SSH or exhausted deadline is a visible state/error, not a fake result.

## 13. Complete CANON coverage and conversion

All 83 CANON columns are accounted for below. Import with a real CSV parser. This schema does not treat every evidence column as a setter.

- Identity/provenance: `config_id` -> evidence.source_config_ids; `model`, `quant`, `engine` -> config identity (normalize Ollama to ollama); `runtime_variant`, `runtime_ref` -> runtime registry/evidence; `candidate` -> profile label; `source` -> evidence source reference.
- Artifacts: `model_file` -> target artifact file manifest; `vision_projector` -> projector artifact/false normalized to null; `draft_model` -> registered draft artifact or integrated-head null. Keep original source values in evidence; do not require client filesystem paths.
- Resources: `gpu`, `gpu_count`, `power_limit_w`, `gpu_layout` -> resource requirements/observed layout, with power read-only on Wright. Free-text layout is parsed only by a verified profile importer.
- Core settings map by name: `context_tokens`, `context_per_slot`, `context_override`, `parallel_slots_per_process`, `replicas`, `gpu_layers`, `main_gpu`, `split_mode`, `tensor_split`, `tensor_overrides`, `batch_size`, `microbatch_size`, `threads_decode`, `threads_prefill`, `kv_type_k`, `kv_type_v`, `flash_attention`, `fit`, `fit_target_mib`, `speculative_mode`, `extra_speculation`, `draft_device`, `draft_tensor_overrides`, `draft_gpu_layers`, `draft_tokens`, `draft_probability_min`, `draft_kv_k`, `draft_kv_v`, `backend_sampling`, `cuda_launch_queues`, `mps`, `force_mmq_runtime`, `load_mode`, `lazy_mode`, `prompt_cache_ram_mib`, `checkpoint_min_step`, `temperature`, `top_k`, `top_p`, `min_p`, `reasoning_effort`. Convert CSV strings to typed arrays/booleans/numbers according to definitions above.
- Build selection/identity: `cuda_graphs_build`, `force_mmq_build`, `force_cublas_build` -> runtime.build_features and optional runtime_requirements, not settings setters.
- Short observation fields: `prefill_tps`, `decode_tps`, `prompt_tokens`, `output_tokens`, `workload`, `rate_scope`, `cache_state`, `observation_id` -> historical measurement. These are not proposed desired speeds or runtime controls.
- Long observation fields: `long_prefill_tps`, `long_decode_tps`, `long_prompt_tokens`, `long_output_tokens`, `long_workload`, `long_rate_scope`, `long_cache_state`, `long_observation_id` -> a separate historical measurement, never mixed into the short example.
- Evaluation lineage: `raw_measurement_count`, `benchmark_controls`, `quality_evidence`, `cautions` -> evidence and test protocol, not raw executable arguments. Preserve failure markers and incomplete quality evidence.
- Lessons: `record_type`, `takeaway`, `evidence_config_ids`, `evidence_ref` -> evidence/lesson objects; qualitative_takeaway rows are not configuration candidates.

Special conversions: `gpu_layers="53/53 (actual target)"` is observed placement, not an integer launch value; recover requested offload from saved profile. `flash_attention="enabled (automatic resolved)"` describes effective state and does not establish the original requested flag. Strings such as `tensor_split="1,1,1"`, `draft_device="CUDA0,CUDA1,CUDA2"` and fit-target lists become typed arrays. `context_override` and `extra_speculation` require typed parsing. Empty CSV cells stay unknown, never assumed false. `load_mode=none` is a real enum value, not null.

4. `changed` becomes `changes` with dotted paths and per-change reasons. Return evidence source IDs and independent validation. Measurements contain explicit timing/cache/token metadata; before/speedup can be null in verify_only.
